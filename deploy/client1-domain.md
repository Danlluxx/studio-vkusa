# Подключение studio-vkusa.ru к хостингу client1

На техническом адресе приложение уже работает. Домен пока указывает на прежний сервер `188.225.23.115`. Доступ `client1` позволяет менять приложение, но не конфигурацию публичного reverse proxy на `179.252.220.236` и его TLS-сертификаты.

## Задача администратора сервера 179.252.220.236

1. Добавить отдельный HTTPS virtual host для `www.studio-vkusa.ru` и `studio-vkusa.ru` в публичный reverse proxy. Внутренний upstream приложения — `http://127.0.0.1:13101`: это порт обратного SSH-туннеля от `client1-http-tunnel.service` к Node-приложению на порту 3101.
2. Проксировать на upstream с заголовками `Host`, `X-Forwarded-Proto` и `X-Forwarded-For`. Разрешить тело запроса до 30 МБ для загрузки медиа в админке. `www` — основной адрес; запросы к корневому домену переводить на него с кодом 301.
3. Выпустить и настроить автоматическое обновление доверенного сертификата сразу для обоих имён. Для HTTP-01 сначала должен быть доступен порт 80 на этом сервере и соответствующие DNS-записи. Возможен DNS-01 при доступе владельца к Timeweb.
4. До смены публичного DNS проверить vhost с принудительным разрешением имени на IP сервера, включая TLS, главную страницу, `/admin/login/`, меню, медиа и редирект с корневого домена.

Только после готовности vhost и сертификата владелец домена меняет в Timeweb записи `A` для `@` и `www` с `188.225.23.115` на `179.252.220.236`. Убедиться, что для этих имён не осталось конфликтующих `AAAA` или `CNAME`.

После переключения на приложении нужно установить `CANONICAL_HOST=www.studio-vkusa.ru` и убрать `STAGING_SITE=1` в `server.mjs`, перезапустить приложение и проверить публичные страницы, формы, медиа, `/admin/`, HTTPS и старые URL. Секреты и SQLite-данные находятся вне Git и не должны заменяться при обновлении кода.

Основной домен переключается только после проверки production-значений и согласования замены прежнего сайта владельцем.
